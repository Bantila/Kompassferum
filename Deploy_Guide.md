# Руководство по деплою Kompassferum

Пошаговая инструкция: подготовка сервера → защита сервера → установка окружения → деплой.

---

## Часть 1. Подготовка сервера

### 1.1 Обновление пакетов

```bash
apt update && apt upgrade -y
```

- `apt update` — обновляет локальный список доступных пакетов и их версий из репозиториев.
- `apt upgrade -y` — устанавливает более новые версии уже установленных пакетов; `-y` автоматически подтверждает все запросы.

### 1.2 Установка Docker

```bash
curl -fsSL https://get.docker.com | sh
```

- `curl -fsSL https://get.docker.com` скачивает установочный скрипт Docker:
  `-f` завершает запрос при HTTP-ошибке, `-sS` убирает прогресс и сохраняет
  сообщения об ошибках, `-L` следует перенаправлениям. `sh` выполняет скрипт.

### 1.3 HTTPS через Caddy

Caddy запускается сервисом в Docker Compose; устанавливать веб-сервер
и Certbot на хост не требуется. Перед запуском направьте DNS домена на IP
сервера и освободите порты 80/tcp и 443/tcp. Для HTTP/3 дополнительно
разрешите 443/udp. Сертификат Caddy получит и будет продлевать автоматически.

Если сервер уже работает с Nginx, сначала выполните раздел
«Переход существующего стенда с Nginx» в [README](README.md).

## Часть 2. Защита сервера

### 2.1 Создать пользователя без root-прав

```bash
adduser deployer
usermod -aG sudo deployer
```

- `adduser deployer` — создаёт нового системного пользователя `deployer` (запросит пароль и данные).
- `usermod -aG sudo deployer` — добавляет пользователя в группу `sudo`, чтобы он мог выполнять команды с повышением прав через `sudo`, не заходя под root напрямую.

### 2.2 Настроить вход по SSH-ключу

На **локальной машине**, если ключа ещё нет:

```bash
ssh-keygen -t ed25519 -C "deploy-key"
```

- `ssh-keygen -t ed25519` — генерирует пару ключей (приватный/публичный) по современному алгоритму Ed25519.
- `-C "deploy-key"` — комментарий-метка для удобства, не влияет на безопасность ключа.

Скопировать публичный ключ на сервер:

```bash
ssh-copy-id deployer@ваш_сервер
```

- `ssh-copy-id` — копирует ваш публичный ключ в файл `~/.ssh/authorized_keys` указанного пользователя на сервере, после чего вход возможен без пароля.

### 2.3 Отключить root-доступ и вход по паролю по SSH

На сервере:

```bash
nano /etc/ssh/sshd_config
```

Найти и изменить (или добавить) строки:

```
PermitRootLogin no
PasswordAuthentication no
```

- `PermitRootLogin no` — запрещает вход по SSH напрямую под root; входить можно только под обычным пользователем и повышать права через `sudo`.
- `PasswordAuthentication no` — отключает вход по паролю, оставляя только вход по SSH-ключу — это устраняет саму возможность брутфорса пароля.

Применить изменения:

```bash
systemctl restart ssh
```

- Перезапускает службу SSH, чтобы новая конфигурация вступила в силу.

> Перед закрытием текущей сессии откройте новое SSH-подключение под `deployer` и проверьте, что вход работает.

### 2.4 Настроить firewall (UFW)

```bash
apt install ufw -y
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw enable
```

- `ufw allow OpenSSH` — разрешает входящие соединения на порт SSH (по умолчанию 22), чтобы не потерять доступ к серверу.
- `ufw allow 80/tcp` и `ufw allow 443/tcp` — открывают порты для HTTP и HTTPS-трафика соответственно.
- `ufw enable` — включает firewall; все остальные входящие порты по умолчанию блокируются.

Проверить статус:

```bash
ufw status verbose
```

### 2.5 Установить Fail2ban

```bash
apt install fail2ban -y
systemctl enable --now fail2ban
```

- `fail2ban` — сервис, который анализирует логи (в первую очередь SSH) и временно банит IP-адреса после нескольких неудачных попыток входа, снижая эффективность брутфорс-атак.
- `systemctl enable --now fail2ban` — включает автозапуск службы при загрузке системы (`enable`) и сразу запускает её (`now`).

### 2.6 Включить автоматические обновления безопасности

```bash
apt install unattended-upgrades -y
dpkg-reconfigure --priority=low unattended-upgrades
```

- `unattended-upgrades` — пакет, автоматически устанавливающий обновления безопасности без ручного вмешательства.
- `dpkg-reconfigure` — открывает диалог настройки; нужно подтвердить включение автоматических обновлений.

## Часть 3. Скачивание исходников и переменные окружения

### 3.1 Клонировать репозиторий

```bash
mkdir -p opt && cd opt
git clone https://github.com/Gemr007/Kompassferum.git
cd Kompassferum
```

- `mkdir -p opt` — создаёт папку `opt` (флаг `-p` не выдаёт ошибку, если папка уже существует).
- `git clone ...` — скачивает исходный код репозитория Kompassferum в текущую папку.
- `cd Kompassferum` — переходит в папку с проектом.

### 3.2 Создать .env файл

```bash
cp .env.example .env
```

- Копирует файл-шаблон переменных окружения в рабочий `.env`, который будет заполняться реальными значениями.

### 3.3 Сгенерировать пароль базы данных (POSTGRES_PASSWORD)

```bash
openssl rand -base64 32 | tr -dc 'A-Za-z0-9' | head -c 32
```

- `openssl rand -base64 32` — генерирует 32 случайных байта и кодирует их в Base64.
- `tr -dc 'A-Za-z0-9'` — оставляет только буквы и цифры, удаляя спецсимволы Base64 (`+`, `/`, `=`).
- `head -c 32` — обрезает результат до 32 символов.

Если `openssl` не установлен:

```bash
apt install openssl -y
```

### 3.4 Сгенерировать JWT-секрет (JWT_SECRET)

```bash
openssl rand -hex 64
```

- Генерирует 64 случайных байта и выводит их в шестнадцатеричном формате — используется как секретный ключ для подписи JWT-токенов.

### 3.5 Сгенерировать секрет вебхука (MAX_WEBHOOK_SECRET)

```bash
openssl rand -base64 64 | tr -dc 'A-Za-z0-9' | head -c 32
```

- Аналогично шагу 3.3, но исходный объём случайных данных больше (64 байта) — используется как секрет для проверки подлинности входящих вебхуков от MAX.

### 3.6 Заполнить .env файл

```bash
nano .env
```

Значения для заполнения:

| Переменная | Что вставить |
|---|---|
| `POSTGRES_PASSWORD` | пароль, сгенерированный в шаге 3.3 |
| `JWT_SECRET` | строка, сгенерированная в шаге 3.4 |
| `GIGACHAT_CREDENTIALS` | Authorization key из личного кабинета developers.sber.ru |
| `MAX_BOT_TOKEN` | токен бота из MAX |
| `MAX_WEBHOOK_SECRET` | пароль, сгенерированный в шаге 3.5 |
| `DOMAIN` | один домен без схемы и пути, например `example.ru` |
| `APP_PUBLIC_URL` | адрес вместе с `https://`, например `https://example.ru` |

Сохранить и выйти из nano: **Ctrl+O** → **Enter** → **Ctrl+X**.

## Часть 4. Деплой

Сначала проверьте конфигурацию:

```bash
docker compose -f docker-compose.yml -f docker-compose.ssl.yml config --quiet
```

`DOMAIN` берётся из заполненного `.env`.

```bash
docker compose -f docker-compose.yml \
  -f docker-compose.ssl.yml \
  up -d --build
```

- `docker compose -f docker-compose.yml -f docker-compose.ssl.yml` — запускает Docker Compose сразу с двумя файлами конфигурации: базовым и SSL-дополнением (второй файл переопределяет/дополняет настройки первого).
- `up` — создаёт и запускает контейнеры, описанные в конфигурации.
- `-d` — режим `detached`: контейнеры работают в фоне, не занимая терминал.
- `--build` — пересобирает образы перед запуском, даже если они уже существуют (полезно после изменений в коде).

Проверить, что контейнеры запущены:

```bash
docker compose -f docker-compose.yml -f docker-compose.ssl.yml ps
```

Посмотреть логи в реальном времени:

```bash
docker compose -f docker-compose.yml -f docker-compose.ssl.yml logs -f
```

- `-f` — режим `follow`: вывод логов продолжается в реальном времени, а не завершается сразу после текущего содержимого.


Проверить публичный HTTPS после выпуска сертификата:

```bash
curl --fail https://example.ru/health
```

Caddy хранит сертификаты в томе `caddy_data`, конфигурацию — в `caddy_config`.
Не удаляйте эти тома при обновлении. Команда `docker compose down -v` удаляет
также PostgreSQL с данными приложения. Healthcheck Caddy проверяет backend
и БД через loopback внутри контейнера; выпуск сертификата проверяется
отдельно запросом к публичному домену.

Полная инструкция, перезагрузка конфигурации и переход с Nginx:
[README — Caddy](README.md#4-caddy-http-локально-и-https-на-домене).

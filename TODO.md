## Проверено на живой платформе

- [x] **MAX.** Развёрнуто на тестовом VPS (Ubuntu 24.04, Docker + nginx +
      Let's Encrypt), вебхук подписан, мини-приложение зарегистрировано в
      кабинете «MAX для партнёров». Проверено вживую: «Начать» в чате даёт
      приветствие, мини-приложение открывается и входит само (аккаунт
      заводится по подписи `initData`, без кода привязки) — подтверждено по
      логам бэкенда на реальном трафике MAX.

      По пути нашлось и починено:
      - `bot_started` разбирался как `message_created` — первое «Начать» не
        давало боту ничего (структура события другая, поля `message` нет);
      - кнопка мини-приложения шла типом `link` вместо `open_app` — initData
        не доходила бы, автовход не сработал;
      - не передавался `format: "html"` — HTML-разметка ответов показывалась
        бы как сырой текст;
      - **MAX подписан НУЦ Минцифры** (Russian Trusted Root/Sub CA) — без
        этого корня любой запрос к MAX падал на проверке TLS
        (`CERTIFICATE_VERIFY_FAILED`), никакого запасного варианта для этого
        нет. Сертификат вшит в репозиторий
        (`app/certs/russian_trusted_ca_bundle.pem`), подключается сам через
        `bot_transport.max_ssl_context()`;
      - `setup_bot.py` падал при `docker compose exec backend python -m
        app.setup_bot --webhook <url>` двумя разными способами: порядок
        аргументов (`--webhook` перед адресом) и попытка писать `.env` внутри
        контейнера, где `/app` root-owned и appuser туда не пишет — оба
        почищены.
      - `DELETE /api/tests/progress` (`status_code=204`, возврат `-> None`
        при активном `from __future__ import annotations`) валил импорт
        роутера и в реальном Docker-образе, не только в локальном pytest —
        починено раньше, чем дошли до деплоя, но фиксирую здесь для памяти.
- [ ] **GigaChat ни разу не ответил вживую.** Код и схема написаны, тесты идут
      на моках. Сбер подписан НУЦ Минцифры, сертификаты которого решено не
      ставить на рабочую машину, поэтому проверка шла только через запасной
      алгоритм. Нужен один реальный прогон на сервере: убедиться, что
      `with_structured_output(method="json_schema", strict=True)` отдаёт ровно
      пять профессий и не падает на длинном ответе.

## Безопасность и приватность

- [ ] **Роль педагога никем не подтверждается.** Сводка по классу отдаётся
      любому пользователю с `role=teacher`, связь «педагог ↔ его класс» не
      проверяется. Для пилота в школе нужен хотя бы код приглашения от
      администратора.
- [ ] **CORS открыт для всех origin** (`allow_origins=["*"]` в `app/main.py`) —
      до тех пор, пока не известен домен мини-приложения MAX. Сузить, как только
      появится.
- [ ] **Нет ограничения частоты запросов.** Ни на вход, ни на `/api/tests/submit`,
      ни на вебхук. Один скрипт может забить базу прохождениями.
- [ ] **Согласия на обработку данных не хранятся.** Сводка ограничена
      k-анонимностью (не формируется, пока тест не прошли хотя бы 3 ученика),
      но реестра согласий нет. Для реальной школы это обязательное условие.

## Качество оценки

- [ ] **Треть банка не задаётся.** В `questions.json` по 13 задач каждой
      сложности, а `test_planner.DIFFICULTIES_IN_PLAN` берёт только `easy` и
      `hard` — все 13 средних вопросов теперь мёртвый груз. Либо задействовать
      их при повторном прохождении, либо убрать из банка.
- [ ] **Банк мал: 3 задачи на предмет.** Для устойчивой оценки нужен пул
      побольше с ротацией, иначе ответы быстро разойдутся между учениками —
      особенно внутри одного класса.
- [ ] **Пороги антифрода — эвристика.** `MIN_SECONDS_KNOWLEDGE = 3.0`,
      `RUSHED_SHARE = 0.4` и остальные подобраны из здравого смысла, а не из
      данных. Когда наберётся хотя бы сотня реальных прохождений — сверить и
      поправить, иначе честные быстрые ученики будут попадать в «недоверие».
- [ ] **Адаптивный подбор не проверялся на людях.** Модель выбирает пять
      предметов по блоку A; насколько выбор осмысленный, видно только на живых
      прохождениях.

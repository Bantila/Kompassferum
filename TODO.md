## Проверено на живой платформе

- [x] **MAX.** Развёрнуто на тестовом VPS (Ubuntu 24.04, Docker + nginx +
      Let's Encrypt), вебхук подписан, мини-приложение зарегистрировано в
      кабинете «MAX для партнёров». Проверено вживую: «Начать» в чате даёт
      приветствие, мини-приложение открывается и входит само (аккаунт
      заводится по подписи `initData`, без кода привязки) — подтверждено по
      логам бэкенда на реальном трафике MAX.

      По пути нашлось и починено:
      - `bot_started` разбирался как `message_created` — первое «Начать» не
        давало боту ничего (структура события другая, поля `message` нет);
      - кнопка мини-приложения шла типом `link` вместо `open_app` — initData
        не доходила бы, автовход не сработал;
      - не передавался `format: "html"` — HTML-разметка ответов показывалась
        бы как сырой текст;
      - **MAX подписан НУЦ Минцифры** (Russian Trusted Root/Sub CA) — без
        этого корня любой запрос к MAX падал на проверке TLS
        (`CERTIFICATE_VERIFY_FAILED`), никакого запасного варианта для этого
        нет. Сертификат вшит в репозиторий
        (`app/certs/russian_trusted_ca_bundle.pem`), подключается сам через
        `bot_transport.max_ssl_context()`;
      - `setup_bot.py` падал при `docker compose exec backend python -m
        app.setup_bot --webhook <url>` двумя разными способами: порядок
        аргументов (`--webhook` перед адресом) и попытка писать `.env` внутри
        контейнера, где `/app` root-owned и appuser туда не пишет — оба
        почищены.
      - `DELETE /api/tests/progress` (`status_code=204`, возврат `-> None`
        при активном `from __future__ import annotations`) валил импорт
        роутера и в реальном Docker-образе, не только в локальном pytest —
        починено раньше, чем дошли до деплоя, но фиксирую здесь для памяти.

## Требует проверки на стенде

- [ ] **GigaChat не работает со стенда.** С рабочей машины модель отвечает
      (26.08.2026, GigaChat-2, строгая схема отрабатывает — проверено
      `python -m app.check_ai`). Но с VPS в Германии недоступен
      `ngw.devices.sberbank.ru` — адрес, где Authorization key меняется на
      токен, по обоим портам, 443 и 9443. При этом `api.giga.chat` оттуда
      доступен. Firewall на сервере выключен, дело не в нём.

      Кодом это не лечится. Варианты: российский хостинг для стенда; обратный
      прокси на российском сервере с подменой `base_url` и `auth_url` (потребует
      прокинуть `auth_url` в клиент — сейчас передаётся только `base_url`); или
      оставить стенд на запасном алгоритме и показывать модель с ноутбука.

      По записи из develop на стенде `AI_PROVIDER=none` — иначе каждый запрос к модели висит
      30 секунд до таймаута, а их два за прохождение.
- [ ] **Проверка TLS для GigaChat.** Корень НУЦ для MAX уже включён в
      `app/certs/russian_trusted_ca_bundle.pem`. Для GigaChat отдельно проверить
      `GIGACHAT_CA_BUNDLE` и `GIGACHAT_VERIFY_SSL` на целевом сервере: локальный
      обход проверки сертификата не подтверждает работу TLS на стенде.

## Безопасность и приватность

- [ ] **CORS открыт для всех origin** (`allow_origins=["*"]` в `app/main.py`) —
      до тех пор, пока не известен домен мини-приложения MAX. Сузить, как только
      появится.
- [ ] **Возраст при согласии не подтверждён.** Ученик называет его сам, и
      проверить его нечем: паспорта у сервиса нет. Правило «до 14 — родитель»
      теперь соблюдается, но опирается на честность ответа.

## Качество оценки

- [ ] **Банк мал: 3 задачи на предмет.** Для устойчивой оценки нужен пул
      побольше с ротацией, иначе ответы быстро разойдутся между учениками —
      особенно внутри одного класса.
- [ ] **Баллы разных попыток сравнимы только на глаз.** Сложность теперь видна
      рядом с результатом, но в балл по-прежнему не входит: формула
      `2/3 -> 3.98` закреплена техзаданием, трогать её нельзя. Настоящая
      сравнимость требует калибровки заданий (IRT) — это отдельная работа с
      реальной статистикой ответов.
- [ ] **Пороги антифрода — эвристика.** `MIN_SECONDS_KNOWLEDGE = 3.0`,
      `RUSHED_SHARE = 0.4` и остальные подобраны из здравого смысла, а не из
      данных. Когда наберётся хотя бы сотня реальных прохождений — сверить и
      поправить, иначе честные быстрые ученики будут попадать в «недоверие».
- [ ] **Адаптивный подбор не проверялся на людях.** Модель выбирает пять
      предметов по блоку A; насколько выбор осмысленный, видно только на живых
      прохождениях.

## Инфраструктура

- [ ] **Тесты не гарантируют, что сборка поднимется.** Локально стоит FastAPI
      0.141, в `requirements.txt` закреплена 0.115.6 — её и ставит образ. Все 180
      тестов проходили, а контейнер не стартовал: на 0.115.6 `-> None` при
      `status_code=204` вместе с `from __future__ import annotations` считается
      схемой ответа. Починено `response_model=None`, но сама расходимость
      осталась. Стоит проверять импорт приложения на закреплённых версиях перед
      деплоем.
- [ ] **На сервере выключен firewall.** `ufw status` — `inactive`, хотя в
      инструкции деплоя он включается. Наружу открыты все порты, а не только 22,
      80 и 443. Включать так, чтобы `ufw allow OpenSSH` шло до `ufw enable`.
- [ ] **`Deploy_Guide.md` дублирует README.** Содержимое перенесено в раздел
      «Деплой на сервер», обе инструкции теперь включены в репозиторий.
      Поддерживать согласованность или оставить один источник инструкции.
- [ ] **Два документа висят удалёнными в git.** `kompas-architecture-pcb.html` и
      `kompas-technical-documentation.docx` перенесены в папку вне репозитория.
      Решить: вернуть в репозиторий или закоммитить удаление.
- [ ] **В истории две параллельные копии прототипа.** У `main` и ветки Романа не

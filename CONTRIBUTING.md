# Как коммитить в «Компас»

Короткий свод правил. Читается за пять минут, экономит часы на разборе истории
перед сдачей.

Главная мысль: **история проекта — это документация решений**. Через неделю
никто не вспомнит, почему поле стало обязательным. Сообщение коммита — то
единственное место, где это можно записать так, чтобы не потерялось.

---

## Формат сообщения

Conventional Commits, заголовок **на русском**:

```
<тип>(<область>): <описание>

<тело: зачем и почему, а не что именно поменялось>

<футер: BREAKING CHANGE, ссылки на задачи>
```

### Заголовок

- **на русском** — проект целиком русский: интерфейс, комментарии, README;
- **глагол в инфинитиве**: `добавить`, `исправить`, `убрать` — не `добавил`,
  не `добавляет`, не `added`;
- **с маленькой буквы, без точки в конце**;
- до 70 символов, чтобы не обрезался в списке коммитов на GitHub.

### Типы

| Тип | Когда |
|---|---|
| `feat` | новая возможность для пользователя |
| `fix` | исправление того, что работало не так |
| `refactor` | код изменился, поведение — нет |
| `test` | только тесты |
| `docs` | только документация |
| `build` | Docker, зависимости, сборка |
| `chore` | служебное: конфиги, чистка |
| `perf` | ускорение |
| `style` | форматирование, пробелы |
| `merge` | слияние ветки (у нас так, вместо авто-сообщения GitHub) |

### Область

Часть проекта в скобках. У нас в ходу: `auth`, `tests`, `ui`, `ai`, `bot`,
`docker`, `demo`, `privacy`, `security`, `readme`, `todo`.

Не обязательна, но с ней список коммитов читается глазами, а не вычитывается.

---

## Тело: пишите «почему», а не «что»

Что поменялось, видно в диффе. Не видно — зачем.

Плохо:

```
fix(ai): добавить min_length в схему

Добавил min_length=1 в поле subjects_to_improve.
```

Хорошо:

```
fix(ai): требовать от модели предметы для улучшения

Первый живой прогон показал: GigaChat возвращает subjects_to_improve пустым
во всех пяти профессиях. Схема это позволяла — у поля не было нижней границы,
а промпт модель вольна проигнорировать.

Ученик при этом терял ответ на второй вопрос продукта: какие предметы стоит
подтянуть. Профессии приходили, совет — нет.
```

Второе через месяц объяснит, почему нельзя «упростить» схему обратно.

Если правка очевидна — опечатка, переименование, — тела не нужно. Одного
заголовка достаточно.

---

## Примеры

**Так — да.** Из нашей истории:

```
fix(tests): не отдавать схему ответа на 204 при сбросе прогресса
feat(auth): подтверждать роль педагога кодом приглашения
docs(todo): уточнить, что мешает GigaChat, и закрыть пункт про стенд
merge(privacy): подключить согласие на обработку данных
```

**Так — нет.** Тоже из нашей истории, всё это пришлось переписывать:

```
Шаг 1: скелет проекта, конфиг, модели БД        ← не тип, а номер шага
Update .env.example                              ← что именно и зачем?
fix: Продолжить с предмета button now navigates  ← смесь языков, не инфинитив
Merge pull request #1 from Bantila/edits         ← авто-сообщение GitHub
```

## Авторство

Коммиты — только от своего имени. **Никаких следов ассистента** в сообщениях:
ни `Co-Authored-By:`, ни `Claude-Session:`, ни упоминаний в теле. Если такая
строка попала в неотправленный коммит — убрать через `git commit --amend`.

Проверить, чем вы подписываетесь:

```bash
git config user.name
git config user.email
```

## Ветки

`develop` — интеграционная, вся работа идёт в неё.
`main` — то, что показывают; вливается из `develop` осознанно.
`roman-clean` — чужая ветка, **не трогать без просьбы владельца**.

Фича делается отдельной веткой от `develop`:

```bash
git switch develop && git pull
git switch -c feat/короткое-имя
# работа, коммиты
git push -u origin feat/короткое-имя
```

Имя ветки латиницей, через дефис: `feat/teacher-invite`, `fix/rate-limit`.

**Грабли с миграциями.** Если параллельных веток несколько и каждая добавляет
миграцию Alembic, номера столкнутся — получатся две головы, и контейнер не
поднимется. У нас так уже было: номер `0010` достался двоим. Вливайте первой
ту ветку, где миграций больше, во второй переномеруйте единственную и
поправьте в ней `down_revision`.

## Перед тем как отправить

```bash
pytest -q
```

Все тесты должны проходить. Если правили фронтенд — пересоберите демо-страницу,
она лежит в репозитории и должна соответствовать коду:

```bash
python demo/build_demo.py
```

**Зелёные тесты не гарантируют, что сборка поднимется.** Локальные версии
библиотек могут отличаться от закреплённых в `requirements.txt`, а в образе
стоят именно закреплённые. На этом уже теряли время: контейнер падал при
импорте, хотя все тесты проходили.

## Если сообщение уже написано неправильно

**Коммит не отправлен** — поправить можно свободно:

```bash
git commit --amend                 # последний
git rebase -i HEAD~3               # один из трёх последних, reword
```

**Коммит уже на GitHub** — переписывание меняет хеши, и у всех остальных
история разойдётся. Нужно:

1. договориться с теми, кто уже мог забрать ветку;
2. переписать и отправить через `git push --force-with-lease`;
3. сказать остальным сделать `git fetch origin && git reset --hard origin/<ветка>`.

`--force-with-lease` вместо `--force` не даст затереть чужие коммиты, если
кто-то успел отправить свои, пока вы переписывали.

## Если вы работаете через ИИ-ассистента

Скопируйте блок ниже целиком и отдайте ассистенту в начале работы — он написан
как набор указаний, а не как объяснение для человека.

```text
Правила работы в репозитории «Компас». Соблюдай их во всех коммитах.

КОММИТЫ
Формат: <тип>(<область>): <описание> — Conventional Commits.
Заголовок на русском, глагол в инфинитиве, с маленькой буквы, без точки в
конце, до 70 символов. Пиши «добавить», а не «добавил», «added» или
«добавляет».
Типы: feat, fix, refactor, test, docs, build, chore, perf, style, merge.
Области в ходу: auth, tests, ui, ai, bot, docker, demo, privacy, security,
readme, todo.
В теле пиши, ЗАЧЕМ сделано изменение и какую проблему оно решает, а не
пересказывай дифф. Если правка очевидна — тела не пиши.
Никогда не добавляй в сообщение Co-Authored-By, Claude-Session и любые другие
упоминания ассистента. Коммит идёт от имени пользователя.
Автоматическое сообщение GitHub «Merge pull request #N from …» заменяй на
merge(<область>): <описание>.

ВЕТКИ
Работа идёт в develop. Фича — отдельной веткой от develop, имя латиницей через
дефис: feat/teacher-invite, fix/rate-limit.
Ветку roman-clean не трогать без явной просьбы владельца.
main вливается из develop осознанно, а не по ходу работы.
Если параллельные ветки добавляют миграции Alembic, номера столкнутся и
получатся две головы — контейнер не поднимется. Вливай первой ту ветку, где
миграций больше; во второй переномеруй единственную и поправь down_revision.

ПЕРЕД ОТПРАВКОЙ
Прогони pytest -q — все тесты должны проходить.
Если правил фронтенд, пересобери демо: python demo/build_demo.py.
Зелёные тесты не гарантируют работающую сборку: версии библиотек локально и в
requirements.txt расходятся, а образ ставит закреплённые. Проверяй, что
приложение импортируется, прежде чем считать работу законченной.

ЕСЛИ СООБЩЕНИЕ УЖЕ ОТПРАВЛЕНО
Переписывание меняет хеши. Сначала предупреди тех, кто мог забрать ветку,
затем push --force-with-lease, затем скажи остальным сделать
git fetch origin && git reset --hard origin/<ветка>.
Никогда не используй --force без --with-lease.

ЯЗЫК
Проект русский целиком: интерфейс, комментарии, документация, сообщения
коммитов. Технические идентификаторы и код остаются как есть.
```

Ассистенты Codex, Cursor и Claude Code подхватывают правила из файла
`AGENTS.md` в корне репозитория автоматически, без копирования. У нас такого
файла в репозитории нет — если решим добавить, копировать блок вручную больше
не понадобится.

## Куда что писать

`README.md` — рассказ о продукте: что это, как запустить, как устроено.
`TODO.md` — известные ограничения и долги. Не в README: там рассказ, а не
список проблем.
`CLAUDE.md` и `AGENTS.md` — памятки для ИИ-агентов, в репозиторий не входят.
